# 오케스트레이션 · 모델 등급 배분

> 여러 서브에이전트/하위 세션으로 일을 나눌 때의 **작업 방식** 문서. 프로젝트 지침이 아니라 워크플로 메타이므로 [AGENTS.md](../../AGENTS.md)에서 분리해 여기 둔다(자동 로드 대상 아님 — 실제로 오케스트레이션할 때만 연다).
> 절차(세션 순서·워크트리·서브세션·ABR 체크리스트)는 [session-playbook.md](session-playbook.md) 참조.

## 병렬 · 격리 · 전문화 (호스트 능력에 따라)

- **네이티브 서브에이전트가 있으면(예: Claude Code의 Agent 툴) 적극 활용한다.** 탐색·리뷰·독립 하위작업을 병렬 에이전트로 분리하고, 결론만 받아 합친다. 병렬로 파일을 동시 수정하면 worktree 격리를 쓴다.
- **네이티브 서브에이전트가 없으면(예: ChatGPT/DevSpace) 대체한다:**
  - **병렬·위험 실험 = 워크트리.** 본 체크아웃을 오염시킬 작업(리팩터, 의존성 bump, 위험 패치)은 새 worktree를 열어 거기서 한다. 워크트리는 격리 수단이지 백업이 아니다 — 끝나면 반드시 커밋한다.
  - **큰 과제 = 서브세션 브리핑.** 큰 과제는 한 대화에 다 넣지 말고, 좁게 스코프한 새 대화를 연다. 첫 메시지에 `AGENTS.md·HANDOFF.md 먼저 읽어라` + 목표 1개 + 건드릴 파일 목록.

## 모델 등급 — 작업의 무게에 비용을 맞춘다

일을 서브에이전트나 하위 세션에 넘길 때, **전부를 최고 성능 모델에 몰지 마라.** 그렇다고 전부를 싼 모델에 맡기지도 마라. 판단 기준은 하나다: **"틀렸을 때 비용이 큰가, 그리고 틀린 걸 알아채기 어려운가."** 그런 일일수록 비싼 모델로, 아니면 싼 모델로 보낸다.

- **비싼(고성능) 모델 — 중요한 "사고" 작업.** 판단·의사결정(어떤 설계를 고를지, 트레이드오프 저울질), 아키텍처·프로토콜 설계(특히 ABR·비트레이트·전송 경로 — 이 프로젝트의 간판이자 회귀 위험이 가장 큰 곳), 검증(어떤 주장·측정·수정이 정말 맞는지 적대적으로 따져보기), 코드·스펙 리뷰와 비평(구멍 찾기), 불변 규칙(AGENTS.md)에 닿는 변경. 이런 일은 정답이 미묘하고, 틀려도 겉보기엔 그럴듯해서 **싼 모델이 "자신 있게 틀리기" 딱 좋은** 영역이다. 여기서는 비용을 아끼지 마라 — 여기서 틀리면 뒤에서 몇 배로 문다.

- **싼(경량) 모델 — 단순·반복·대량 작업.** 기계적 수정(대량 rename, 정해진 패턴의 리팩터), 대량 수집·요약(여러 파일 훑어 목록 만들기, 로그·PCAP 파싱, 벤치 결과 표 정리), 보일러플레이트·테스트 스캐폴딩처럼 **정답이 분명하고 검증이 쉬운** 일. 처리량이 목적인 팬아웃(넓게 훑기)은 싼 모델로 넓고 병렬로 돌린다.

- **섞을 땐 이렇게.** 넓게 훑고 긁어모으는 단계는 싼 모델로 병렬 처리하고, 그 결과를 놓고 **무엇을 할지 정하고 합치는 단계만 비싼 모델**에 맡긴다(팬아웃은 싸게, 판단·합성은 비싸게). 그리고 싼 모델의 대량 산출물을 **그대로 믿지 마라** — 테스트·컴파일 같은 자동 체크나 고성능 모델의 스팟 리뷰로 한 번 걸러라. 싼 모델의 진짜 비용은 요금이 아니라 **애매한 일에서의 잘못된 확신**이다.

## Ultracode(최대 노력) 모드에서 — 등급이 품질을 해치지 않게

등급 규칙은 ultracode와 **충돌하지 않는다.** ultracode는 "얼마나 철저히"(커버리지)를, 등급은 "그 철저함을 어떻게 배분"(효율)을 정한다 — 두 축은 직교한다. "비용은 제약이 아니다"는 *돈 아끼려 작업을 건너뛰지 마라*는 뜻이지 *모든 하위작업에 최고 모델을 낭비하라*가 아니다. 등급을 제대로 쓰면 같은 예산으로 팬아웃이 넓어져 **오히려 더 ultracode다워진다.** 단, 오분류가 품질을 무너뜨리는 경로가 있어 아래 4개를 강제한다:

1. **목적은 절약이 아니라 재배치다.** 싼 모델로 아낀 예산은 청구서를 줄이는 데 쓰지 말고 **검증 패스·커버리지 확대에 재투자**한다.
2. **등급 분류 판단은 오케스트레이터(고성능)가 한다.** "이 작업이 어느 등급인가"를 싼 모델에게 묻지 말고, 태스크 레이블("스캐폴딩·파싱·기계적 수정")에 등급을 묵시적으로 위임하지 마라. **난이도가 애매하면 타이브레이커는 항상 고성능** — 애매할 때 다운그레이드 금지.
3. **경량 산출물엔 검증 게이트가 필수.** 싼 모델 결과가 판단·합성의 입력이 될 때는 자동 검증(컴파일·테스트 통과) 또는 고성능 스팟 리뷰를 **반드시** 거친다(생략 시 ultracode 미충족). 싼 서브에이전트에겐 "분류 경계를 벗어난다고 느끼면 즉시 ESCALATE 보고" 의무를 줘라 — 신호가 오면 재분류하고 오염된 결과는 재사용하지 말고 버린다.
4. **겉보기 기계적이어도 아래는 무조건 고성능으로 에스컬레이션** (팬아웃 대상에서 제외): `unsafe`·`#[repr(*)]`·수동 비트/오프셋 연산에 닿는 변경 / 프로토콜 불변식(재생방지 윈도우, 시퀀스 번호 경계, 클록 드리프트 허용치)을 단언하는 테스트 생성 / 파싱 결과를 이상 판단·ABR 입력으로 직접 쓰는 파이프라인. (이 목록은 코드가 진화하면 갱신한다.)
