betterparsec — 저지연 원격제어, 만들 가치가 있나

사지방 공용 PC에서 집 Windows PC로. 3차에 걸친 다중 에이전트 리서치로 “Sunshine이 Parsec보다 낫다”를 엄격히 검증하고, 실제 만들 수 있는 아키텍처와 정직한 빌드 vs 구매 판정까지 정리한다.

3× multi-agent 워크플로 34건 적대적 검증 전송 = Cloudflare WARP (고정) 2026-07
한 줄 결론

재페어링은 이미 해결된 문제(빌드 불필요)이고, 진짜 병목은 인증이 아니라 WARP 연결성 + 적응형 비트레이트 부재다. 그런데 당신의 실제 불만인 “뭉개짐”을 막아주는 게 적응형 비트레이트인데 — 그건 Parsec엔 있고 Sunshine 계열엔 없다. 그래서 뭉개짐만 놓고 보면 Parsec이 솔직히 더 나은 도구다.

01

화질 “뭉개짐”의 원인 순위

코덱은 가장 작은 레버다. 지배 요인은 전송(WARP)이고, 그 다음이 레이트컨트롤과 4:2:0 크로마다. 막대 폭은 정량 측정이 아니라 기여도의 정성 순위다.

왜 WARP인가

무료 WARP은 처리량을 ~50% 삭감하고 CONFIRMED, edge-relay라 jitter/loss가 붙는다. UDP가 완전 차단되면 TCP 443 폴백 CONFIRMED — 실시간 스트림이 TCP 터널로 들어가면 HoL 블로킹으로 그 자체가 뭉개짐을 만든다.

왜 코덱은 작은가

하드웨어 AV1은 HEVC 대비 ~15–25%(한 눈금). 큰 스크린콘텐츠 이득(HEVC-SCC −57%, palette/IBC)은 소프트웨어 인코더 전용이라 실시간 GPU 경로엔 실현되지 않는다 CONFIRMED. 하드웨어엔 AV1+4:4:4가 아예 없다.

02

재페어링 — 공짜로 해결됨, 코드 불필요

유일하게 번거롭다던 “매 세션 재페어링”은 커스텀 코드 없이 없앨 수 있다. CONFIRMED

방법 A · 네이티브

포터블 Moonlight + 신원 복원

페어링된 신원(cert/key/uniqueid + 호스트 cert)을 미리 심은 포터블 폴더를 실행 → PIN 없이 즉시 mutual-TLS 연결.

  • 장점: 무설치급, 코드 0
  • 단점: 공용 PC에 private key 노출, 집 sunshine_state.json 고정 필요
방법 B · 브라우저

moonlight-web-stream (서버측 페어링)

페어링을 서버측 JSON에 저장 → 브라우저는 로그인만, 재페어링 원천 없음. Vibeshine도 Sunshine 웹UI 계정 세션 기반. CONFIRMED

  • 장점: 무설치 + 재페어링 0 + key가 서버측
  • 단점: WebRTC 경로 → 연결성·화질은 §4 이슈

참고: Sunshine/Apollo에 계정·토큰 인증 기능은 없다 CONFIRMED — 위 두 방법이 “계정처럼” 동작하게 만드는 우회다.

03

빌드 vs 구매 — 정직한 판정

Parsec Warp 유료는 DIY가 가장 고전하는 3가지(계정 인증 · 4:4:4 · 적응형 비트레이트)를 이미 제공한다. 그리고 당신 네트워크에선 Parsec이 이미 된다.

대부분의 경우 이김

Parsec Warp 유료 · $8.33–9.99/월

  • ✅ 계정 인증(1회 로그인, 재페어링 0)
  • ✅ 10-bit 4:4:4 — 색 텍스트 번짐 제거
  • ✅ BUD 적응형 비트레이트 — jitter 뭉개짐 방지
  • → 뭉개짐 두 축을 동시에 침
이럴 때만 이김

DIY betterparsec

  • 구독 회피 + 자가호스트 소유·제어
  • 무료 4:4:4 / AV1 그 자체가 목적
  • Parsec이 그 망에서 막히는데 자가 443은 뚫릴 때
  • ⚠️ jitter 구간 화질은 오히려 열위(적응성 부재)
04

만든다면 — 확정 아키텍처

최소 미검증 의존성으로 “1회 로그인 · 재페어링 0 · WARP에서 볼 만함”을 만족하는 스택: 브라우저 WebRTC/WebCodecs + 서버측 계정 인증 + coturn TURN-over-TLS(443).

전송 부품은 전부 오늘 존재하나, Cloudflare edge + VPS 릴레이 경유 게임 지연은 미검증 CONTEXT-DEP — Phase 0에서 반드시 실측.

06

단계별 계획 — 측정 먼저, 그다음 MVP

Phase 0 · 사전 de-risk1–2일

아무것도 짓기 전에: ① 대상 망에서 Parsec 연결되나(build-vs-buy를 좌우) ② 대상 PC → 공인 VPS로 outbound TCP 443 뚫리나(curl/iperf) ③ 브라우저 Chrome 버전·chrome://gpu 코덱 확인.

Phase 1 · MVP~1주

증명 목표 = “1회 로그인 · 재페어링 0 · WARP에서 볼 만함”. 집 Sunshine → moonlight-web-stream 계정 1개·호스트 1회 서버측 페어링 → VPS coturn TLS/443 + relay-only ICE → 사지방 브라우저 접속. 검증: wipe 후 재로그인만으로 재페어링 없이 연결.

Phase 2 · 화질 하드닝~1주

대상 브라우저/GPU에서 HEVC·AV1 HW 디코드 실제 확인(안 되면 H.264 수용). WARP 하한 아래 보수적 고정 비트레이트 + 완만 FEC, HW 허용 시 4:4:4/10-bit.

Phase 3 · 보안 하드닝~1–2주

토큰 전 필드 서명 · 짧은 수명+refresh(공용 PC엔 refresh 미저장) · 상수시간 비교 · replay/nonce · 안전 인코딩 · HttpOnly/Secure · least-privilege. Vibeshine 채택 시 AI 생성 인증 코드 정밀 감사 필수.

Phase 4 · (선택) 품질 천장규모 큼 · 불확실

사용가능 UDP 전송이 실측 확인되면 네이티브 Moonlight로 지연 개선; 또는 rtpgccbwe→NVENC 적응형을 자체 배선(무겁고 오늘 존재하지 않음).

사지방 이용수칙은 필터 우회·원격접속을 명시 금지하고, 사용이 로깅되며 위반 시 징계·계정삭제 소지가 있다(근거: 국방부 훈령 「사이버지식정보방 운영 및 관리에 관한 훈령」). WARP 설치 자체가 우회로 걸릴 수 있다. 기술적 성공 ≠ 사용 허용. 규정 리스크 없는 환경(집 외부망·휴가지)을 기준으로 설계·사용 권장.

추천 다음 스텝
  1. 무빌드로 뭉개짐 직격: Parsec Warp 4:4:4 켜기 + WARP 실 대역폭/jitter 측정. 대부분 여기서 해결될 가능성이 높다.
  2. 그래도 소유권·무구독이 목적이면: Phase 0 측정 → moonlight-web-stream + coturn + compose 스캐폴딩으로 MVP 착수.
  3. 대역폭이 상한이면: WARP+(Argo smart routing) 라우팅 개선 시도 — 그 이상은 물리적 한계.
