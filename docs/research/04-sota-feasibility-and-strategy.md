# 리서치 4 — "Parsec을 전 축에서 이기는 시스템"의 실현 가능성 판정과 전략 (2026-07)

> 목표: Parsec보다 뛰어난 화질 + 더 낮은 지연 + 더 적은 네트워크로 초고화질·초고프레임.
> 질문: 최신/실험적 코덱·기법으로 가능한가? 새로 개발해서라도 가능한가? 어떻게 진행하나?

_다중 에이전트 웹 리서치 4트랙(코덱 SOTA / 전송 SOTA / 경쟁사 teardown / 지연 한계 기법) + 기존 리서치 1–3 종합. 2026-07-14._

---

## 0. 한 줄 결론

**가능하다 — 단, "새 코덱 개발"이 아니라 "전송·파이프라인 엔지니어링"으로.**
2026년 현재 어떤 실험적 코덱(VVC/AV2/LCEVC/뉴럴)도 실시간 4K120 브라우저 스트리밍에 쓸 수 없고,
쓸 필요도 없다. Parsec의 실제 해자(BUD 적응형 전송, 2018년 설계)는 그 뒤에 나온 공개 연구
(Pudica NSDI'24, SCReAM v2, Tetrys RFC 9407, L4S)로 **정면 돌파 가능**하며, Parsec의 코덱 스택
(H.264/HEVC, 50 Mbps 캡, AV1 없음)은 이미 우리 하드웨어(RTX 4070, AV1 10-bit 검증 완료)에
뒤처져 있다. 승부처는 코덱이 아니라 **① 혼잡제어+FEC, ② 서브프레임 파이프라인, ③ 클라이언트
프레젠트 경로, ④ 계측 진실성**이다.

## 1. 축별 실현 가능성 판정

### 1-A. 화질 (같은 비트레이트에서 Parsec보다 선명) — **가능, 이미 구조적 우위**

- Parsec: H.264/HEVC만, **AV1 없음**, ~50 Mbps 캡, 4:4:4는 유료(Warp $9.99/mo)+NVIDIA/Intel 전용.
- 우리: NVENC AV1 10-bit 4:2:0(RTX 4070 실검증 완료) — H.264 대비 ~40%, HEVC 대비 ~20-30%
  비트레이트 절감. HEVC 10-bit 4:4:4 인코드도 호스트에서 검증 완료. 150 Mbps+ 가능.
- **제약 1**: AV1 4:4:4 하드웨어 인코더는 존재하지 않음(Ada/Blackwell 공통, 실리콘 한계).
  → 모션/게임 = AV1 4:2:0 10-bit, 텍스트/데스크톱 = HEVC 4:4:4 프로파일 토글(기존 설계 유지).
- **제약 2 (신규 발견)**: HEVC 4:4:4는 브라우저에서 **하드웨어 디코드 불가**
  (NVDEC/AMD VCN 모두 미지원, Chrome≥117은 SW 폴백). 4:4:4 웹 경로는 CPU 디코드 비용을
  지불하는 "텍스트 모드"로 한정하고, 고fps 게임 프로파일로 광고하지 않는다.
  하드웨어 4:4:4 디코드가 필요하면 네이티브 클라이언트(NVDEC 직접) 경로가 유일하다.
- 판정 기준은 ROADMAP hard gate 그대로: 동일 wire bitrate에서 VMAF-NEG +2 이상.

### 1-B. 초저지연 — **가능하되 2단계: 웹 클라로 동급, 네이티브 클라로 왕좌**

물리적 하한(LAN, 실측·문헌 종합):

| 단계 | 최적화 값 |
|---|---|
| 캡처(DDA, VRAM 포인터) | ~0 ms |
| 색변환(GPU 셰이더) | 0.1–0.5 ms |
| NVENC ULL 인코드 | 1080p ~2–4 ms (4K는 문헌 상충 — §3 참조, 자체 실측 필수) |
| LAN 전송 | 0.2–1 ms |
| HW 디코드 | 2–4 ms |
| 렌더/프레젠트 | 네이티브 1–2 ms / **브라우저 +1 rAF(4–8 ms) 구조적 추가** |
| 디스플레이 스캔아웃 | 120Hz 평균 4.2 ms / 240Hz 평균 2.1 ms / VRR·tearing ~0 |

- **하드 플로어 ≈ 4–6 ms** (LAN·240Hz·네이티브·최적화 전부). Parsec 자체 측정 4–8 ms(240fps,
  2018 HW)와 정합. **120Hz 네이티브 ~10 ms, 웹 클라 ~15–25 ms**가 현실적 목표선.
- Parsec을 이기는 미개척 수단 3개(업계 아무도 출하 안 함):
  1. **서브프레임 슬라이스 파이프라인**: NVENC `sliceMode` + `enableSubFrameWrite` +
     `constrainedFrame`으로 슬라이스 NAL 단위 조기 전송·조기 디코드. RTX 4070 단일 NVENC에서도
     가능. 공개 실측 부재 → 우리가 최초 측정·출하 기회.
  2. **클라이언트 VRR/immediate-flip 프레젠트**: `DXGI_PRESENT_ALLOW_TEARING`으로 수신 즉시
     표시. 120–240Hz에서 4–8 ms 회수. Moonlight조차 미구현(요청만 존재). 네이티브 클라 전용.
  3. **커널 레벨 입력 주입**: raw-input 게임에서 `SendInput`은 오동작(카메라 스냅).
     GameStream/Parsec 방식의 서명된 커널 HID 드라이버가 정답. (게임패드는 ViGEmBus로 충분.)
- 웹 클라이언트 지연 최소화: `playout-delay` ext(min=max=0) + `jitterBufferTarget=0`(Chrome 124+)
  + WebCodecs를 Worker + WebGPU `importExternalTexture`로(“copyTo() 금지”, `<video>` 회피).
- **결론**: 웹 클라로는 Parsec 웹앱(SW 디코드, MSE)을 압도하고 Parsec 네이티브와 동급까지.
  hard gate(입력-포톤 median 2 ms 개선)를 Parsec 네이티브 상대로 넘으려면 네이티브 클라 +
  위 3개 수단이 필요하다.

### 1-C. 네트워크 효율 (적은 비트로 동급+ 화질) — **가능, 가장 확실한 축**

- 코덱: AV1로 Parsec(H.264/HEVC) 대비 20–40% 절감 — hard gate(총 wire bytes 20%↓)를 코덱만으로
  거의 충족.
- FEC: Moonlight는 고정 ~20% RS 오버헤드, WebRTC FlexFEC 기본은 ~40% 오버헤드.
  **적응형 FEC(손실 관측 기반) + Tetrys(RFC 9407, 슬라이딩 윈도우)**로 평시 오버헤드를
  한 자릿수%로 낮추면서 <20 ms 복구 유지 — 실시간용으로 블록 FEC(RaptorQ류) 대비 유일하게 적합.
- 혼잡제어: 현 ABR(REMB+loss, GCC류)은 시작점. SOTA는 **Pudica(NSDI 2024)** 스타일
  프레임-딜레이 기반 CC — 프로덕션에서 프레임딜레이 3.1×/p95 4.9× 감소, 비트레이트 +12%.
  Rust 스트리머라 브라우저 CC 제약 없이 구현 가능(브라우저에 탑재된 CC는 GCC뿐).
- L4S: Comcast DOCSIS 시험 + T-Mobile 5G SA 전국(2025-07) — 실재하지만 경로 한정.
  ECT(1)+SCReAM v2를 **선택적 옵트인**으로(비 L4S 병목에서 starvation 위험 있어 기본 off).

### 1-D. 초고해상도 + 초고프레임 (4K120+) — **조건부 가능**

- 인코드: RTX 4070 단일 NVENC로 4K 처리량 HEVC P1 288fps / AV1 P1 212fps — **4K120 충분**.
  (SFE는 듀얼 NVENC 필요라 4070은 불가 — 필요 없음, 슬라이스 모드는 별개로 가능.)
- 디코드: 클라이언트 HW AV1 디코드 필요(RTX30+/RDNA2+/Intel 11세대+/M3+). Chrome/Edge
  WebCodecs 커버리지 ~91.5%.
- 240fps: 1080p/1440p에서 현실적. 4K240은 인코더·디코더·전송 모두 무리 — 목표에서 제외.
- 저대역 초고화질의 열쇠: **1440p 인코드 + 클라이언트 RTX VSR 업스케일**(드라이버 레벨,
  Chrome/Edge에서 공짜, 2026-01 브라우저 스트리밍 개선 발표). 대역 절반으로 4K급 체감.
  WebGPU SR(websr류)은 120fps 실측 부재 — 후순위.
- 물리 법칙: "초고화질 4K120"과 "극단적 저대역"은 상충. 정직한 포지션 =
  4K120 AV1 40–80 Mbps(LAN/양호 WAN) 또는 1440p120 15–25 Mbps + VSR.

## 3. 상충 증거·미검증 항목 (자체 실측 필요)

1. **4K NVENC 인코드 지연**: arXiv 2511.18687/2605.01187은 4K에서 5프레임(HQ tuning, 일부는
   ULL도 5프레임 주장) 파이프라인 지연을 보고. 반면 Sunshine 실사용/우리 loopback은 host
   processing p50 2.2 ms(1080p), 커뮤니티 4K165 인코드 ~4 ms 보고. 측정 방법(타임코드 촬영,
   플레이어 포함) 차이로 추정 — **RTX 4070에서 ULL+슬라이스 설정으로 직접 실측이 P0**.
2. 서브프레임 슬라이스의 실제 절감량: 이론 (인코드+전송+디코드 겹침) ~수 ms — 공개 실측 없음.
3. WebCodecs 디코드 지연의 브라우저별 편차: 문헌 부재. 우리 계측 스택으로 측정.
4. Parsec FEC 사용 여부: DTLS 암호화로 미확인.
5. 독립 glass-to-glass 벤치마크는 **업계 전체에 2024–2026 공백** — 우리 photodiode/1000fps
   하네스가 그대로 신뢰성 자산이 된다(측정 자체가 마케팅 가능한 산출물).

## 4. 비용 배분 — 비싸게 갈 곳 / 싸게 갈 곳

### 비싸게 (여기서 이긴다 — 시간·노력 집중)
1. **계측 하네스 완성** (P0 잔여: packet capture 교차검증, 외부 광학 계측, ABBA 러너 실전 run).
   모든 주장의 근거이자 업계 공백. 하드웨어 비용은 소액(photodiode+MCU ~수만원, 고속카메라
   대안은 240fps 폰 슬로모로 시작).
2. **전송 계층 (Rust 스트리머)**: 프레임딜레이 기반 CC(Pudica류) + 적응형 Tetrys FEC +
   프레임 페이싱. Parsec BUD의 해자를 정면으로 넘는 무기. 기존 F1 ABR 위에 증축.
3. **서브프레임 슬라이스 파이프라인**: 인코드→전송→디코드 겹침. 선점 기회.
4. **(후순위) 네이티브 클라이언트**: 지연 왕좌용 — VRR/tearing 프레젠트 + NVDEC 4:4:4 +
   커널 입력. 웹 클라 gate 통과 후 착수.

### 싸게 (기성품·설정·공짜 레버)
- AV1 10-bit 협상 + HEVC 4:4:4 토글 — 대부분 배선 완료, 검증만.
- RTX VSR 하이브리드(1440p 인코드+클라 업스케일) — 문서화+권장 설정만.
- `playout-delay`/`jitterBufferTarget=0`/WebCodecs Worker+WebGPU 렌더 — 소규모 웹 작업.
- coturn 릴레이 — 저가 VPS 1대(기존 F2 계획 그대로).
- L4S — ECT(1) 마킹+감지 코드만, 인프라 투자 없음.
- **GPU 업그레이드 불필요**: Blackwell은 +5% 품질/4:2:2뿐, AV1 4:4:4 여전히 없음. RTX 4070
  인코드 처리량은 4K120에 충분. 지금 돈 쓸 곳 아님.

### 사지 않는다 / 만들지 않는다
- 새 코덱, 뉴럴 코덱, VVC/LCEVC 라이선스, MoQ 인프라(지금은), 4K240 목표.

## 5. 로드맵 반영 (기존 M0–M4에 증분)

- **P0 추가**: RTX 4070 ULL/슬라이스 인코드 지연 자체 실측(§3-1 상충 해소).
- **M2 확장**: ABR 컨트롤러를 프레임딜레이 신호(Pudica류)로 진화 + 적응형 FEC(고정 20% 탈피).
- **M3 유지**: AV1 10-bit 기본 + HEVC 4:4:4 텍스트 프로파일. 4:4:4 웹 경로는 SW 디코드임을
  truth table에 명시(광고 금지 항목).
- **M5 신설 — 서브프레임/렌더 경로**: NVENC 슬라이스 파이프라인, playout-delay=0,
  WebCodecs Worker+WebGPU 프레젠트, 1440p+VSR 프로파일.
- **M6 신설(선택) — 네이티브 클라이언트**: VRR/tearing 프레젠트, NVDEC 직결, 커널 입력 주입.
  착수 조건: 웹 클라가 hard gate에서 Parsec 웹앱 전승 + Parsec 네이티브 동급 달성 후.
- **중기 관망**: WebTransport+WebCodecs 전송 전환(지터버퍼 완전 우회), SCReAM v2/L4S 옵트인.

## 6. 결정 사항 (이 판정이 전제한 가정)

1. **"Parsec보다 낫다"의 조작적 정의 = ROADMAP hard gates** (VMAF-NEG +2, 입력-포톤 median
   2ms/p95 5ms, wire bytes 20%↓ 등) — 기존 문서의 정의를 그대로 채택. 바꾸려면 ROADMAP
   §hard gates를 수정.
2. **주 환경 = 집 LAN + 양호한 WAN** (사지방 규정 리스크는 리서치 1 §5 결론 유지 — 실사용
